Настоящий API-сценарий: `tests/integration/message-storage.test.ts`. По умолчанию он пропущен, не читает `.env.local` и не входит в обычный `tests/*.test.ts`. Он создаёт трёх временных пользователей, диалоги и небольшие файлы, проверяет listing/download/info/createSignedUrl, точные байты, legacy, отмену, group avatar, удалённого участника и anonymous; в `finally` удаляет только созданные им пути/диалоги/аккаунты. При аварийном завершении процесса автоматическая очистка не гарантируется.

Используйте **отдельный одноразовый тестовый Supabase-проект** с последовательностью миграций, включая `202610300001_private_message_uploads.sql`, `202610130002_dating.sql` и `202611020001_group_contact_safety.sql`. Для текущего раннера также нужна `202611020002_group_invitations.sql`. Скрипт сам не применяет миграции; production-проект NEXUS жёстко запрещён. Не создавайте и не меняйте облачную инфраструктуру без разрешения владельца. Сохраните вне Git игнорируемый `.env.storage-test.local`:

```dotenv
NEXUS_STORAGE_TEST_RUN=1
NEXUS_STORAGE_TEST_URL=
NEXUS_STORAGE_TEST_PROJECT_REF=
NEXUS_STORAGE_TEST_PUBLISHABLE_KEY=
NEXUS_STORAGE_TEST_SERVICE_ROLE_KEY=
```

URL/ref должны совпадать с выбранным тестовым проектом (`https://<ref>.supabase.co`); для локального Supabase ref равен `local`. В `NEXUS_STORAGE_TEST_SERVICE_ROLE_KEY` задаётся серверный secret API key (`sb_secret_…`) либо legacy service_role выбранного тестового проекта. Он используется **только** локальным тестовым раннером для временных fixtures, не приложением или браузером. Не используйте ключи production, не сохраняйте их в Git/выводе тестов. Команды из корня проекта, Node.js 24:

```sh
node --experimental-strip-types --test tests/group-chats-database.test.ts
node --experimental-strip-types --test tests/integration/message-storage.test.ts
node --env-file=.env.storage-test.local --experimental-strip-types --test tests/integration/message-storage.test.ts
```

Вторая команда без opt-in должна явно показать `SKIP`; это не пройденный интеграционный тест. Третья изменяет только явно выбранный тестовый проект. Для подготовки review: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, `git diff --check`.

**Граница доступа.** Pending-файл читает только загрузивший его текущий участник. Другие участники читают его после ссылки из разрешённого RLS сообщения (одиночный старый формат или массив) либо как сохранённое фото группы. Новая политика не меняет INSERT/DELETE и owner-проверку metadata перед отправкой; типы/API не меняются.

**Отмена и сироты.** Существующая кнопка × удаляет собственный выбранный объект через Storage API. При закрытии вкладки/неясном результате отправки незавершённые загрузки могут остаться: теперь они приватны и не становятся видны собеседнику. Автоматическая очистка по одному возрасту не добавлена — она могла бы удалить файл одновременно с публикацией; такую очистку нужно отдельно согласовать и проверить. Не удаляйте строки `storage.objects` вручную вместо Storage API.

**Signed URL.** Новая RLS-политика ограничивает получение свежих ссылок, но уже выданная ссылка остаётся bearer-доступом; удаление membership/выход не отзывают её мгновенно. Кэш и уже скачанные байты проверяются отдельно; одного TTL недостаточно для обещания мгновенного отзыва. Реальный тест намеренно проверяет работоспособность ранее выданной ссылки после удаления участника. См. [Supabase downloads](https://supabase.com/docs/guides/storage/serving/downloads) и [Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn).

## Проверка нового Supabase-проекта

Используйте отдельный проект без реальных студенческих данных. Примените миграцию и выполните настройку Auth по README. Подготовьте два разных email для учётных записей **A** и **B**. Для независимых сессий используйте разные браузеры или обычное и приватное окно.

### 1. Регистрация и сессия

- Зарегистрировать A, получить настоящее письмо, подтвердить email.
- Войти и обновить защищённую страницу: сессия сохраняется.
- Проверить неправильный пароль и повторную регистрацию без раскрытия чувствительных данных.
- Выйти и открыть `/feed` напрямую: требуется вход.
- Без сессии открыть профиль, публикацию и будущие разделы: данные недоступны.
- Проверить недействительную и уже использованную ссылку подтверждения: контролируемая ошибка.

### 2. Профиль и интересы

- Заполнить имя, фамилию, username, описание, специальность, курс, группу и HTTPS-аватар.
- Выбрать несколько интересов, сохранить и обновить страницу.
- Изменить выбор и убедиться, что удалённые интересы исчезли, новые появились.
- Очистить необязательные поля и интересы; сохранение остаётся корректным.
- В B занять username и в A попытаться сохранить тот же username: понятная ошибка, прежние поля и интересы A сохранены без частичного изменения.
- Проверить ограничения длины и недопустимый URL аватара.
- Открыть профиль B из A; кнопки изменения чужих данных отсутствуют.

### 3. Посты и комментарии

- A создаёт текстовый пост; B видит его в ленте с автором и датой.
- Открыть профиль автора и вернуться в ленту.
- Открыть публикацию, A и B добавляют по комментарию.
- A удаляет собственный комментарий, комментарий B остаётся.
- Проверить пустой/слишком длинный текст и быстрое повторное нажатие кнопки.
- Создать достаточное число публикаций для второй страницы и проверить порядок и навигацию.
- Открыть несуществующую публикацию и username: корректное состояние отсутствия записи.

### 4. RLS через API

Проверяйте именно запросы от пользовательских сессий с публичным ключом. SQL Editor выполняет административные запросы и не доказывает безопасность обычного клиента.

- Анонимный клиент не получает профили, посты и комментарии.
- A не изменяет и не удаляет профиль, пост и комментарий B.
- A не создаёт пост/комментарий с `author_id` B.
- A не изменяет `profile_interests` B.
- Обычный пользователь не меняет каталог `interests`.
- Попытка записать несуществующий interest/post/author отклоняется внешними ключами.
- Ошибка сохранения профиля откатывает изменение интересов и полей целиком.
- Удаление собственного тестового поста через API удаляет его комментарии каскадно. Кнопки удаления поста в интерфейсе MVP нет.
- Попытка подменить ID, дату создания, автора или перенести комментарий на другой пост отклоняется правами на столбцы.

Учитывайте семантику RLS: запрещённый UPDATE/DELETE может вернуть ноль изменённых строк без отдельной ошибки. Проверяйте итоговую запись от имени владельца, а не только HTTP-статус запроса.

### 5. Интерфейс и переносимость

- Проверить главную, формы, ленту и профиль на узком экране и на компьютере.
- Пройти формы с клавиатуры: фокус виден, подписи понятны, ошибки читаемы.
- Убедиться, что `/messages`, `/map`, `/ai` показывают заглушки и не имитируют готовую функцию.
- Открыть приложение без env: доступна инструкция настройки.
- Распаковать отдельную копию без `node_modules` и `.next`; выполнить `npm ci` и build.
- Повторить запуск на втором целевом OS, если доступен. Проверка на Mac не равна проверке на Windows.

### Два реальных пользователя

Примените миграцию к **отдельному тестовому Supabase-проекту**, настройте приложение и создайте два подтверждённых тестовых аккаунта. В корне проекта создайте игнорируемый Git файл `.env.test.local`:

```dotenv
NEXUS_E2E_LIVE=1
NEXUS_E2E_EMAIL=first-test@example.com
NEXUS_E2E_PASSWORD=replace-with-test-password
NEXUS_E2E_OTHER_EMAIL=second-test@example.com
NEXUS_E2E_OTHER_PASSWORD=replace-with-other-test-password
```

URL и публичный ключ Supabase берутся из `.env.local`; они должны относиться к тому же проекту, с которым работает проверяемый сервер. Логины выше — примеры, замените их своими выделенными тестовыми аккаунтами. Запустите `npm run test:e2e`.

Сценарий проверяет вход A → сохранение профиля и интереса → публикацию → сохранение сессии после обновления → выход → вход B → профиль автора → комментарий → удаление своего комментария → заглушки → выход → защиту страниц. В `finally` он удаляет созданный пост по уникальному маркеру и восстанавливает прежние поля и интересы A, используя публичный ключ и сессию владельца. Если очистка не удалась, тест завершается ошибкой; проверьте тестовый проект вручную.

### Отдельная проверка регистрации

Для нового тестового email добавьте отдельное разрешение:

```dotenv
NEXUS_E2E_SIGNUP=1
NEXUS_E2E_SIGNUP_EMAIL=new-test@example.com
NEXUS_E2E_SIGNUP_PASSWORD=replace-with-new-test-password
```

Тест выполняет настоящий запрос регистрации и проверяет сообщение о подтверждении либо переход в профиль, если Supabase выдаёт сессию сразу. **Доставку письма и переход по ссылке он не проверяет. Созданный аккаунт остаётся в тестовом проекте**; при необходимости удалите его через Supabase Dashboard. Повторная регистрация того же email может вернуть нейтральное сообщение — это не доказательство создания нового аккаунта.
