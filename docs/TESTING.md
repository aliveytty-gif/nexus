## Что доказывают разные проверки

| Проверка | Что проверяет | Чего не подтверждает |
| --- | --- | --- |
| TypeScript | Согласованность типов исходного кода. | Реальную схему удалённой базы. |
| ESLint | Правила качества кода. | Работу пользовательского сценария. |
| Локальные автоматические тесты | Валидаторы и проверяемые инварианты схемы/RLS. | Доставку email и работу размещённого Supabase Auth. |
| Production build | Возможность собрать приложение Next.js. | Успешный вход пользователя в настроенном проекте. |
| Браузерная проверка без credentials | Главную страницу, адаптивность, навигацию и состояние настройки. | Регистрацию, запись постов и серверные права в Supabase. |
| Интеграционная проверка с Supabase | Настоящие Auth, данные и права двух пользователей. | Будущие функции и эксплуатационную готовность при высокой нагрузке. |

## Подключение Supabase — 21 сентября 2026

Создан отдельный проект NEXUS на Free в Frankfurt. Исходная миграция применена один раз через SQL Editor 20 сентября к пустой базе; история миграций CLI при этом не заполнялась. Локальная конфигурация приложения находится в игнорируемом `.env.local` и не входит в архив.

| Проверка | Результат |
| --- | --- |
| Удалённая схема | 8/8 SQL-проверок: пять таблиц с RLS и ожидаемыми политиками/SELECT grants, триггер профиля, права RPC, семь интересов. |
| Auth API | `/auth/v1/health` и `/auth/v1/settings` отвечают HTTP 200; email включён, signup разрешён, подтверждение email обязательно. |
| Анонимный Data API | Все пять таблиц возвращают HTTP 401 с кодом `42501`, как ожидается после отзыва SELECT у `anon`. |
| Сборка с подключением | Production build с `.env.local` и проверкой TypeScript успешен; ESLint — без ошибок и предупреждений. Сервер перезапущен. |
| Браузер без сессии | Формы входа/регистрации доступны; семь защищённых маршрутов перенаправляют на `/login?next=...`. |
| Реальная регистрация и письмо | Ещё не проверены: требуется регистрация пользователя и подтверждение письма. |
| Запись профиля/постов/комментариев, два пользователя | Ещё не проверены на размещённом проекте; нужны подтверждённые пользовательские сессии. |

Site URL — `http://localhost:3000`; разрешены `/auth/callback`, `/auth/callback?next=/profile/edit` и `/auth/confirm` на этом адресе. Используется стандартный email-шаблон с `{{ .ConfirmationURL }}` и существующий PKCE callback приложения. В этом Free-проекте Dashboard не разрешает редактирование шаблона без custom SMTP; custom SMTP пока не настроен. Для стандартного письма нужен тот же браузер и cookie, что при регистрации.

Встроенная отправка Supabase ограничена адресами участников организации. До подключения собственного SMTP регистрация произвольного студенческого email с подтверждением не готова. Успешные SQL/API-проверки не подтверждают доставку письма или работу пользовательских записей через Auth.

## Подключение Brevo SMTP — 22 сентября 2026

| Проверка | Результат |
| --- | --- |
| Сохранение custom SMTP | Проверено в новой вкладке Supabase Dashboard: custom SMTP включён, отправитель — NEXUS с подтверждённым Gmail-адресом, сервер — `smtp-relay.brevo.com`, порт — `587`, логин — из настроек SMTP Brevo. Несохранённых изменений нет. |

Ссылка использует `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&amp;type=email&amp;next=/profile/edit`; в HTML `&amp;` становится `&` в адресе. Предпросмотр Dashboard показывает русский текст, несохранённых изменений нет. |
| Доставка письма и подтверждение NEXUS | Ещё не проверены: сохранение SMTP не подтверждает отправку, получение письма или создание сессии. |

Текущий шаблон направляет пользователя на серверный маршрут `/auth/confirm`: он проверяет `token_hash` через Supabase и сохраняет сессию в cookie. Исходная cookie PKCE для этого потока не требуется. При локальном Site URL письмо нужно открывать на компьютере с работающим NEXUS по адресу `http://localhost:3000`.

Личный адрес отправителя и SMTP key в документацию и архив не включаются. Подтверждение Gmail в Brevo относится к отправителю; регистрацию пользователя NEXUS нужно проверить отдельно.

## Локальная проверка

Из корня проекта после `npm ci`:

```sh
npm run typecheck
npm run lint
npm test
npm run build
```

Тесты запускаются штатным тестовым раннером Node.js с поддержкой TypeScript. Проверка миграции использует PGlite — локальный PostgreSQL-совместимый движок для тестов. Тестовое окружение создаёт имитацию необходимых Auth-ролей и идентификатора пользователя. Это позволяет проверять SQL и изоляцию записей без ключей и облачной базы, но не заменяет проверку реального Supabase.

Для проверки собранного приложения:

```sh
npm start
```

Не запускайте dev-сервер и production-сервер одновременно на одном порту.

## Проверка нового Supabase-проекта

Используйте отдельный проект без реальных студенческих данных. Примените миграцию и выполните настройку Auth по README. Подготовьте два разных email для учётных записей **A** и **B**. Для независимых сессий используйте разные браузеры или обычное и приватное окно.

### 1. Регистрация и сессия

- Зарегистрировать A, получить настоящее письмо, подтвердить email.
- Войти и обновить защищённую страницу: сессия сохраняется.
- Проверить неправильный пароль и повторную регистрацию без раскрытия чувствительных данных.
- Выйти и открыть `/feed` напрямую: требуется вход.
- Без сессии открыть профиль, публикацию и будущие разделы: данные недоступны.
- Проверить недействительную и уже использованную ссылку подтверждения: контролируемая ошибка.

### 2. Профиль и интересы

- Заполнить имя, фамилию, username, описание, специальность, курс, группу и HTTPS-аватар.
- Выбрать несколько интересов, сохранить и обновить страницу.
- Изменить выбор и убедиться, что удалённые интересы исчезли, новые появились.
- Очистить необязательные поля и интересы; сохранение остаётся корректным.
- В B занять username и в A попытаться сохранить тот же username: понятная ошибка, прежние поля и интересы A сохранены без частичного изменения.
- Проверить ограничения длины и недопустимый URL аватара.
- Открыть профиль B из A; кнопки изменения чужих данных отсутствуют.

### 3. Посты и комментарии

- A создаёт текстовый пост; B видит его в ленте с автором и датой.
- Открыть профиль автора и вернуться в ленту.
- Открыть публикацию, A и B добавляют по комментарию.
- A удаляет собственный комментарий, комментарий B остаётся.
- Проверить пустой/слишком длинный текст и быстрое повторное нажатие кнопки.
- Создать достаточное число публикаций для второй страницы и проверить порядок и навигацию.
- Открыть несуществующую публикацию и username: корректное состояние отсутствия записи.

### 4. RLS через API

Проверяйте именно запросы от пользовательских сессий с публичным ключом. SQL Editor выполняет административные запросы и не доказывает безопасность обычного клиента.

- Анонимный клиент не получает профили, посты и комментарии.
- A не изменяет и не удаляет профиль, пост и комментарий B.
- A не создаёт пост/комментарий с `author_id` B.
- A не изменяет `profile_interests` B.
- Обычный пользователь не меняет каталог `interests`.
- Попытка записать несуществующий interest/post/author отклоняется внешними ключами.
- Ошибка сохранения профиля откатывает изменение интересов и полей целиком.
- Удаление собственного тестового поста через API удаляет его комментарии каскадно. Кнопки удаления поста в интерфейсе MVP нет.
- Попытка подменить ID, дату создания, автора или перенести комментарий на другой пост отклоняется правами на столбцы.

Учитывайте семантику RLS: запрещённый UPDATE/DELETE может вернуть ноль изменённых строк без отдельной ошибки. Проверяйте итоговую запись от имени владельца, а не только HTTP-статус запроса.

### 5. Интерфейс и переносимость

- Проверить главную, формы, ленту и профиль на узком экране и на компьютере.
- Пройти формы с клавиатуры: фокус виден, подписи понятны, ошибки читаемы.
- Убедиться, что `/messages`, `/map`, `/ai` показывают заглушки и не имитируют готовую функцию.
- Открыть приложение без env: доступна инструкция настройки.
- Распаковать отдельную копию без `node_modules` и `.next`; выполнить `npm ci` и build.
- Повторить запуск на втором целевом OS, если доступен. Проверка на Mac не равна проверке на Windows.

## Браузерные тесты Playwright

По умолчанию `npm run test:e2e` запускает публичные сценарии и явно пропускает два live-сценария. API не подменяется. При отсутствии уже работающего сервера Playwright запускает dev-сервер на `http://127.0.0.1:3000`.

```sh
npx playwright install chromium
npm run test:e2e
```

Для проверки production предварительно выполните `npm run build` и `npm start`; затем запустите тесты во втором терминале. Для другого адреса задайте `NEXUS_E2E_BASE_URL`: с этой переменной Playwright использует указанный сервер и не запускает свой.

### Два реальных пользователя

Примените миграцию к **отдельному тестовому Supabase-проекту**, настройте приложение и создайте два подтверждённых тестовых аккаунта. В корне проекта создайте игнорируемый Git файл `.env.test.local`:

```dotenv
NEXUS_E2E_LIVE=1
NEXUS_E2E_EMAIL=first-test@example.com
NEXUS_E2E_PASSWORD=replace-with-test-password
NEXUS_E2E_OTHER_EMAIL=second-test@example.com
NEXUS_E2E_OTHER_PASSWORD=replace-with-other-test-password
```

URL и публичный ключ Supabase берутся из `.env.local`; они должны относиться к тому же проекту, с которым работает проверяемый сервер. Логины выше — примеры, замените их своими выделенными тестовыми аккаунтами. Запустите `npm run test:e2e`.

Сценарий проверяет вход A → сохранение профиля и интереса → публикацию → сохранение сессии после обновления → выход → вход B → профиль автора → комментарий → удаление своего комментария → заглушки → выход → защиту страниц. В `finally` он удаляет созданный пост по уникальному маркеру и восстанавливает прежние поля и интересы A, используя публичный ключ и сессию владельца. Если очистка не удалась, тест завершается ошибкой; проверьте тестовый проект вручную.

### Отдельная проверка регистрации

Для нового тестового email добавьте отдельное разрешение:

```dotenv
NEXUS_E2E_SIGNUP=1
NEXUS_E2E_SIGNUP_EMAIL=new-test@example.com
NEXUS_E2E_SIGNUP_PASSWORD=replace-with-new-test-password
```

Тест выполняет настоящий запрос регистрации и проверяет сообщение о подтверждении либо переход в профиль, если Supabase выдаёт сессию сразу. **Доставку письма и переход по ссылке он не проверяет. Созданный аккаунт остаётся в тестовом проекте**; при необходимости удалите его через Supabase Dashboard. Повторная регистрация того же email может вернуть нейтральное сообщение — это не доказательство создания нового аккаунта.

### Настройки запуска

| Переменная | Назначение |
| --- | --- |
| `NEXUS_E2E_BASE_URL` | Адрес уже запущенного приложения, например `http://localhost:3000`. |
| `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` | Необязательный путь к установленному Chrome вместо скачанного Chromium. |
| `NEXUS_E2E_LIVE` | Только значение `1` вместе с четырьмя параметрами аккаунтов включает сценарий с записью данных. |
| `NEXUS_E2E_SIGNUP` | Только значение `1` и параметры нового аккаунта включают регистрацию. |

Приоритет env: уже заданные переменные процесса → `.env.test.local` → `.env.local`. После изменения настроек перезапустите проверяемый сервер; для production заново выполните build. Не сохраняйте `.env.test.local` в Git или ZIP. Для live-сценариев запись trace, видео и скриншотов отключена, чтобы не сохранять введённые данные аккаунтов.

Пропуск live-тестов не означает успешную проверку Supabase Auth или пользовательского сценария.

## Как фиксировать результат

В отчёте указывайте дату, ОС, Node.js, команду/сценарий и итог. Для интеграции отмечайте, что применена текущая миграция, не публикуя credentials или адреса личной почты. Разделяйте `пройдено`, `ошибка` и `не выполнялось`.

После исправления ошибки повторяйте связанные проверки. Не расширяйте тестирование до будущих модулей, пока они представлены заглушками.
