# План развития NEXUS

Цель на учебный 2026–2027 год — постепенно построить внутреннюю среду колледжа, где участники находят людей с общими интересами и делятся жизнью колледжа. Этапы упорядочены по зависимостям; это план, а не обещание календарных сроков.

## Phase 1 — Core MVP

### Состав первой версии

- Email/password Auth, подтверждение адреса, вход, выход и сохранение сессии.
- Профили и редактирование собственных данных.
- Нормализованный каталог интересов и выбор тегов.
- Хронологическая лента с пагинацией.
- Текстовые посты и отдельная страница публикации.
- Плоские комментарии и удаление своих комментариев.
- Навигация к заглушкам Messages, College Map и NEXUS AI.
- Миграции, RLS, типы, документация и переносимая npm-сборка.

### Критерии приёмки

- Новый разработчик запускает ZIP на другом компьютере по README.
- На реальном тестовом Supabase-проекте проходит цепочка «регистрация → подтверждение → профиль → пост → чужой профиль → комментарий → выход».
- Второй пользователь видит разрешённый контент и не может изменить чужие записи через UI или API.
- Ошибки сети, пустая лента и отсутствие настроек имеют понятное отображение.
- TypeScript, lint, тесты и production build проходят; результаты отражены в TESTING.

**Статус:** код Phase 1 подготовлен; факт приёмки зависит от результатов проверок в [TESTING.md](TESTING.md), включая реальную интеграцию с Supabase.

## Phase 2 — Social

### Порядок внедрения

1. **Лайки.** Таблица с уникальной парой пользователь/пост, RLS для собственных реакций, счётчик без повторного голоса.
2. **Поиск пользователей.** Username, имя, специальность и группа; ограниченные ответы и пагинация.
3. **Подбор по интересам.** Прозрачное пересечение `profile_interests`; объяснение, какие интересы совпадают.
4. **Личные сообщения.** Диалоги, участники и сообщения; RLS доступа по участию. После проверки обычной отправки — realtime, статусы и вложения.

**Готовность:** доступны только разрешённые профили и диалоги, нет дублей реакций, проверены ограничения доступа минимум для трёх пользователей. Прежде чем открывать платформу всему колледжу, отдельно решить ограничение регистрации, жалобы на контент, удаление данных и назначение ответственных за поддержку.

## Phase 3 — College

1. **College map.** Получить настоящие планы и актуальные названия помещений. Создать этажи, кабинеты и точки интереса; сначала поиск кабинета и карточка, затем маршруты.
2. **Events.** Мероприятия с датой, местом, организатором и статусом; определить, кто отвечает за актуальность.
3. **Clubs / communities.** Сообщества, участие и публикации в сообществе. Расширять права по конкретной потребности.

**Готовность:** данные сверены с колледжем, карта полезна на телефоне, помещения имеют стабильные ID, просроченные события не выглядят актуальными.

## Phase 4 — Intelligence

1. **База знаний колледжа.** Структурированные материалы о кабинетах, службах, расписании работы и контактах; владелец источника и дата обновления.
2. **Поиск.** Сначала обычный поиск по проверенным данным; семантический поиск добавлять при подтверждённой необходимости.
3. **NEXUS AI.** Ответы со ссылками на источники. При отсутствии данных — честное сообщение и контакт ответственного. Выбор модели и стоимости отдельной задачей.
4. **Рекомендации.** Объяснимые подсказки людей и мероприятий по интересам; возможность отказаться от персонализации.

**Готовность:** ответы проверяются на наборе реальных вопросов, устаревшая информация выявляется, приватные данные не выходят за разрешённые границы, расходы ограничены. Например, ответ про кабинет 305 должен опираться на запись карты, а время работы библиотеки — на действующий источник.

## Правила перехода между этапами

- Добавлять один небольшой проверяемый результат за раз.
- Новые сущности поставлять вместе с миграциями, RLS и обновлением типов.
- Перед новой функцией исправлять проблемы существующих сценариев.
- Не добавлять инфраструктуру без измеримой потребности.
- Проверять переносимость на чистой установке и обновлять README при изменении команд.
- Не считать заглушку или успешную сборку доказательством готовности бизнес-сценария.

До подтверждённой потребности не планируются микросервисы, Kubernetes, собственная авторизация, сложный глобальный store и отдельная административная система.
