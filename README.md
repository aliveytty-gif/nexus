# NEXUS

Внутренняя социальная платформа колледжа. Первый этап — регистрация, профили и интересы, хронологическая лента, текстовые публикации и комментарии. Проект предназначен для постепенной разработки в течение учебного 2026–2027 года.

Это исходный код приложения для локального запуска. Готовый Supabase-проект, ключи доступа и пользовательские данные в архив не входят.

## Что уже есть в коде

- Главная страница с описанием NEXUS, входом и регистрацией.
- Email/password через Supabase Auth, выход и обновление сессии.
- Защищённые разделы приложения.
- Профили `/profile/[username]`: имя, фамилия, username, аватар, описание, специальность, курс, группа, интересы и дата регистрации.
- Редактирование собственного профиля. Интересы выбираются из общего каталога и хранятся отдельно от профиля.
- `/feed`: текстовые публикации, авторы, даты, переходы в профили, хронологическая выдача с пагинацией.
- Страница публикации с комментариями и удалением собственных комментариев.
- `/messages`, `/map`, `/ai`: страницы «Раздел находится в разработке».
- SQL-миграция со связями, ограничениями и Row Level Security (RLS).
- Адаптивный интерфейс, состояния пустых списков, ошибок и отсутствующей настройки Supabase.

Загрузка файлов пока не реализована: аватар задаётся HTTPS-ссылкой на изображение. Личные сообщения, карта и AI пока представлены только точками расширения.

## Стек

Next.js 16.3.5 с App Router, React 19.3, TypeScript, Tailwind CSS 4.3, Supabase Auth и PostgreSQL. Пакеты устанавливаются через npm. Точные версии закреплены в `package.json` и `package-lock.json`.

Страницы преимущественно рендерятся на сервере. Изменения выполняются через Server Actions, а доступ к данным дополнительно контролируется PostgreSQL RLS. Собственной системы паролей, отдельного API-сервера, Redux и платного AI API нет.

## Быстрый путь

1. Установите Node.js 24 LTS.
2. Распакуйте проект и откройте терминал в папке, содержащей `package.json`.
3. Выполните `npm ci`.
4. Создайте Supabase-проект и примените SQL из `supabase/migrations/202609150001_core.sql`.
5. Скопируйте `.env.example` в `.env.local` и заполните URL и публичный ключ проекта.
6. Настройте email/password и адреса подтверждения в Supabase Auth.
7. Выполните `npm run dev`, откройте [localhost:3000](http://localhost:3000) и зарегистрируйтесь.

Подробные инструкции ниже помогают пройти эти шаги с нуля.

## 1. Установите Node.js

Скачайте **Node.js 24 LTS** с [официального сайта Node.js](https://nodejs.org/en/download). Для Mac выберите установщик macOS; для Windows — Windows Installer. npm устанавливается вместе с Node.js. После установки откройте новое окно терминала.

Проверьте:

```sh
node --version
npm --version
```

`node --version` должен показывать `v24.x.x`. Используйте одинаковую основную версию Node.js на обоих компьютерах. В проекте есть `.nvmrc` для пользователей nvm; устанавливать nvm специально не требуется.

Для работы через Git установите [Git](https://git-scm.com/downloads). Для первого запуска ZIP-архива Git не обязателен.

## 2. Получите проект и установите зависимости

Если получили ZIP, полностью распакуйте его. Не запускайте команды внутри просмотра архива.

Если используете Git:

```sh
git clone <адрес-вашего-репозитория> nexus
cd nexus
```

В терминале Mac или PowerShell Windows перейдите в распакованную папку:

```sh
cd "путь/к/nexus"
npm ci
```

Команда `npm ci` устанавливает версии из приложенного `package-lock.json`. Обычная `npm install` также поддерживается; используйте её, когда намеренно меняете зависимости. Изменённый lock-файл сохраняйте вместе с `package.json`.

## 3. Создайте Supabase-проект

1. Создайте учётную запись на [supabase.com](https://supabase.com/).
2. В [Dashboard](https://supabase.com/dashboard) создайте проект, задайте название, регион и надёжный пароль базы данных.
3. Дождитесь завершения создания проекта.
4. В настройках подключения/API найдите **Project URL** и **publishable key**.

Пароль PostgreSQL и `service_role`/secret key приложению не нужны. Публичный ключ используется вместе с RLS: он не даёт права обходить политики доступа.

### Примените миграцию через SQL Editor

Для первого запуска Supabase CLI не нужен:

1. В Dashboard откройте **SQL Editor → New query**.
2. Откройте `supabase/migrations/202609150001_core.sql` из проекта в текстовом редакторе.
3. Скопируйте весь файл в SQL Editor и выполните его.
4. Убедитесь, что выполнение завершилось без ошибок. В схеме `public` появятся `profiles`, `posts`, `comments`, `interests`, `profile_interests`.

Применяйте исходную миграцию **один раз к новому проекту**, до регистрации первых пользователей. Она создаёт схему, каталог интересов и триггер профиля. Данные старых пользователей из другого проекта она не переносит.

Если в Supabase-проекте уже есть свои таблицы или пользователи, сначала изучите миграцию и используйте отдельный тестовый проект. Последующие изменения оформляйте новыми файлами миграций; уже применённую миграцию не переписывайте.

### Альтернатива: Supabase CLI

При командной разработке можно вести миграции через [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started). Из корня проекта:

```sh
npx supabase login
npx supabase link --project-ref <идентификатор-проекта>
npx supabase db push
```

Убедитесь, что ссылка ведёт на нужный проект. `db push` изменяет удалённую базу. Не применяйте ту же исходную миграцию сначала в SQL Editor, а затем повторно через CLI: ручное применение не создаёт автоматически запись в истории CLI. Для перехода на CLI сверяйте историю по [инструкции по миграциям](https://supabase.com/docs/guides/deployment/database-migrations).

Запуск локального стека Supabase через контейнеры для этого MVP не требуется.

## 4. Добавьте переменные окружения

**macOS / Linux / Git Bash:**

```sh
cp .env.example .env.local
```

**Windows PowerShell:**

```powershell
Copy-Item .env.example .env.local
```

Откройте `.env.local` в редакторе:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

| Переменная | Значение |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL вашего Supabase-проекта. |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Publishable key из настроек проекта. |
| `NEXT_PUBLIC_SITE_URL` | Адрес приложения. Для инструкции ниже — `http://localhost:3000`. |

Для старых Supabase-проектов поддерживается `NEXT_PUBLIC_SUPABASE_ANON_KEY` как запасной вариант вместо publishable key. Если заданы оба ключа, используется publishable key. Никогда не подставляйте сюда `service_role` или secret key: переменные `NEXT_PUBLIC_*` доступны браузеру.

`.env.local` исключён из Git и не должен входить в ZIP. После изменения переменных перезапустите dev-сервер. Для production выполните `npm run build` заново: значения `NEXT_PUBLIC_*` закрепляются при сборке. Без корректных переменных приложение показывает страницу настройки; вход и доступ к базе до настройки недоступны.

## 5. Настройте Supabase Auth

В Supabase Dashboard:

1. Откройте **Authentication → Sign In / Providers** и включите Email с паролем.
2. Оставьте подтверждение email включённым для проверки владения адресом.
3. В **Authentication → URL Configuration** задайте **Site URL**: `http://localhost:3000`.
4. В **Redirect URLs** добавьте:

   ```text
   http://localhost:3000/auth/callback
   http://localhost:3000/auth/callback?next=/profile/edit
   http://localhost:3000/auth/confirm
   ```

5. В **Authentication → Email Templates → Confirm signup** настройте ссылку подтверждения на серверный маршрут приложения:

   ```html
   <a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email&next=/profile/edit">Подтвердить email для NEXUS</a>
   ```

Маршрут `/auth/confirm` проверяет одноразовый `token_hash` через Supabase и сохраняет сессию в cookie. `/auth/callback` предусмотрен для обмена PKCE-кода на сессию. Не помещайте `token_hash`, коды подтверждения и cookie в логи или публичные сообщения.

Настройки шаблона и разрешённых URL находятся в Supabase, а не в коде приложения: при создании нового проекта задайте их заново. Подробнее: [password-based auth](https://supabase.com/docs/guides/auth/passwords), [SSR с Next.js](https://supabase.com/docs/guides/auth/server-side/nextjs), [redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).

Письма отправляет Supabase. Ограничения отправки зависят от конфигурации проекта; если реальное письмо не приходит, проверьте Auth Logs, настройки почты и раздел спама. Не считайте регистрацию проверенной до получения письма и успешного подтверждения.

Для будущего допуска только по корпоративной почте потребуется серверное ограничение регистрации на стороне Supabase Auth. Одной проверки домена в форме недостаточно: API Auth можно вызвать напрямую.

## 6. Запустите приложение

```sh
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000). Если порт 3000 уже занят, освободите его либо согласованно измените адрес в `.env.local`, Supabase Site URL и Redirect URLs.

Первая проверка:

1. Зарегистрируйтесь на реальный email и подтвердите его по письму.
2. Войдите и заполните собственный профиль, выберите интересы.
3. Создайте текстовую публикацию, найдите её в ленте и откройте.
4. Добавьте комментарий и удалите его.
5. Во втором браузере зарегистрируйте второго пользователя, откройте его профиль из ленты.
6. Выйдите; защищённые страницы должны снова требовать вход.

В исходном проекте нет вымышленных аккаунтов и публикаций. До появления первого поста лента показывает настоящее пустое состояние.

## 7. Проверка качества и production build

```sh
npm run typecheck
npm run lint
npm test
npm run build
npm start
```

`npm start` запускает уже собранное приложение. Для реальных Auth/DB-сценариев нужны заполненные переменные окружения и подготовленный Supabase-проект. Успешная сборка сама по себе не подтверждает доставку писем, регистрацию и политики в вашем удалённом проекте.

Описание уровней проверки и ограничений: [docs/TESTING.md](docs/TESTING.md).

## 8. Перенос на другой Mac или Windows

### Продолжить с теми же пользователями и публикациями

1. Передайте исходную папку через Git или ZIP.
2. Не включайте `node_modules`, `.next`, `.env.local`, логи и результаты браузерных тестов.
3. На новом компьютере установите Node.js 24 LTS.
4. В папке проекта выполните `npm ci`.
5. Создайте `.env.local` и укажите **тот же Supabase-проект**.
6. Выполните `npm run dev`.

Код, конфигурация и миграции находятся в репозитории. Аккаунты, профили, посты и комментарии находятся в Supabase. Поэтому копирование папки переносит разработку, а подключение к тому же Supabase-проекту сохраняет доступ к тем же данным. Сессии браузера между компьютерами не копируются — войдите заново.

### Начать с новой базы

Создайте новый Supabase-проект, примените миграцию, настройте Auth и замените переменные окружения. Получится та же структура приложения с пустыми пользовательскими данными.

### Перенести существующие данные в другой Supabase-проект

Это отдельная операция: SQL-миграции схемы не являются резервной копией данных или аккаунтов. Используйте [официальные инструкции по переносу Supabase-проекта](https://supabase.com/docs/guides/platform/migrating-within-supabase) и [резервному копированию](https://supabase.com/docs/guides/platform/backups). Отдельно учитывайте Auth, настройки почты, redirect URLs и, если Storage будет добавлен позже, объекты Storage. До переключения приложения проверьте восстановление на тестовом проекте.

## 10. Продолжить разработку через Codex

Откройте **корневую папку NEXUS**, где лежит `package.json`, как проект Codex. Передайте задачу, например:

> Изучи AGENTS.md, README.md, docs/ARCHITECTURE.md и docs/ROADMAP.md. Продолжи NEXUS: реализуй поиск пользователей по username и интересам из Phase 2. Сохрани RLS, оформи изменения БД новой миграцией и проверь typecheck, lint, тесты и production build. Не добавляй другие модули.

Для каждой функции задавайте небольшой проверяемый результат. Изменения схемы сохраняйте в новой миграции, обновляйте TypeScript-типы и документацию. Не передавайте Codex секретные ключи в сообщениях и не просите отключить RLS для устранения ошибок.

После изменения схемы можно получить актуальный TypeScript-контракт командой `npx supabase gen types typescript --linked --schema public`. Сверьте результат с `src/types/database.ts`, сохранив используемые проектом экспорты `Profile`, `Post`, `Comment` и `Interest`; затем запустите typecheck. Команда требует ранее выполненного `supabase link`.

## Если что-то не запускается

| Симптом | Что проверить |
| --- | --- |
| Открывается страница настройки | `.env.local` лежит рядом с `package.json`, URL и ключ заполнены; сервер перезапущен. |
| `relation ... does not exist` | Миграция успешно применена в том же проекте, чей URL указан в `.env.local`. |
| `Invalid API key` | Использован publishable/anon key правильного проекта, без лишних кавычек или пробелов. |
| `Database error saving new user` | Миграция и триггер профиля установлены; подробнее — Auth Logs и PostgreSQL Logs в Dashboard. |
| Подтверждение возвращает ошибку | Site URL, Redirect URLs, email-шаблон; ссылка могла истечь или уже быть использована. |
| `Email not confirmed` | Подтверждение email ещё не завершено. Откройте актуальное письмо регистрации. |
| Изменение данных отклонено | Пользователь вошёл, редактирует собственную запись, значения соответствуют ограничениям. Не отключайте RLS. |
| `npm ci` сообщает несовпадение lock-файла | После намеренного изменения `package.json` выполните `npm install` и сохраните оба файла. |
| Порт 3000 занят | Остановите другой сервер или обновите согласованно все адреса Auth и приложения. |


### Ошибка наблюдения за файлами на Mac

Если `next dev` сообщает `EMFILE: too many open files, watch` или повторно перезапускается, остановите его и включите polling только для этого запуска:

```sh
WATCHPACK_POLLING=1000 npm run dev
```

В PowerShell аналогичная настройка задаётся так:

```powershell
$env:WATCHPACK_POLLING="1000"
npm run dev
```

Это запасной режим наблюдения за файлами; обычная команда запуска остаётся `npm run dev`. Production-сервер `npm start` наблюдение за файлами не использует.
