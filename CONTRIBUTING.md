# Совместная разработка NEXUS

Этот документ предназначен для разработчиков, GitHub-коллабораторов и ИИ-агентов. Цель — независимо развивать модули одного продукта, сохраняя совместимость и безопасность всей платформы.

**Статус правил.** Уже действующие ограничения берутся из [AGENTS.md](AGENTS.md), кода и проверяемой конфигурации. Ниже они дополнены **предлагаемым организационным регламентом**: Task Contract, фиксация `BASE_COMMIT`, согласование общих файлов, обязательное ревью и Integration Manifest. Эти дополнения требуют одобрения Maintainer в PR этого документа; не следует выдавать их за ранее действовавшие или автоматически обеспеченные GitHub правила. Рекомендации по именованию и настройкам GitHub обозначены отдельно.

Документ не назначает конкретных людей владельцами модулей, не предоставляет доступ к данным и не заменяет [AGENTS.md](AGENTS.md). При противоречии зафиксируйте документы, наблюдаемое поведение и затронутую задачу, затем запросите решение Maintainer. Работающий код показывает реализацию, но сам по себе не разрешает нарушать требования безопасности.

## 1. Философия и начало работы

- Один продукт и основной репозиторий: [aliveytty-gif/nexus](https://github.com/aliveytty-gif/nexus). Личный fork может быть источником PR, но не становится альтернативной основной версией.
- Сохраняйте модульность, общую архитектуру и визуальную идентичность. Ищите существующее решение перед созданием нового компонента, сервиса или слоя данных.
- Меняйте минимально необходимое. Не объединяйте задачу с массовым форматированием, сменой стека или необязательным рефакторингом.
- Стабильность, безопасность и совместимость важнее количества новых возможностей. Не дублируйте Auth, чаты, квоты, Storage helpers и другие работающие системы.
- Поддерживайте macOS и Windows: регистр имён импортов, относительные пути и команды не должны зависеть от личной папки разработчика. Не утверждайте, что ОС проверена, если запуск не выполнялся.
- Экономьте ресурсы ИИ: читайте нужные разделы, объединяйте связанные изменения и не повторяйте успешные проверки без новых изменений или причины.

### Локальный запуск

Используйте Node.js **24**, как в [.nvmrc](.nvmrc) и CI, и npm не ниже 10. `package.json` допускает Node.js от 22.12.0, но для совместной работы выбирайте одинаковую основную версию с CI.

```sh
git clone https://github.com/aliveytty-gif/nexus.git
cd nexus
node --version
npm --version
npm ci
```

Создайте файл окружения:

```sh
# macOS / Linux / Git Bash
cp .env.example .env.local
```

```powershell
# Windows PowerShell
Copy-Item .env.example .env.local
```

Заполните `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` и `NEXT_PUBLIC_SITE_URL=http://localhost:3000`. Поддерживаемый запасной ключ — `NEXT_PUBLIC_SUPABASE_ANON_KEY`; это не `service_role`. Названия и назначение параметров смотрите в [.env.example](.env.example) и [src/lib/env.ts](src/lib/env.ts).

Используйте отдельный тестовый Supabase-проект с актуальной схемой. Для новой пустой базы последовательно примените SQL из [supabase/migrations](supabase/migrations/) по имени файла, а не только первую core-миграцию. Перед каждым применением проверяйте целевой проект и историю уже выполненных миграций; при несовпадении истории остановитесь и согласуйте её восстановление. Ручное выполнение в SQL Editor не заполняет автоматически историю CLI. Не повторяйте миграции в существующей базе ради «чистого запуска».

Настройте локальные Auth Site URL/redirect URLs по README, сохраняя production-настройки отдельного проекта. Затем:

```sh
npm run dev
```

Откройте `http://localhost:3000`, зарегистрируйте выделенного тестового пользователя и подтвердите email. Без настройки Supabase часть публичных экранов доступна, но это не проверка Auth, данных или RLS. Для работы над другими модулями AI-ключ не требуется; не копируйте production-секреты в личное окружение. Сверяйте существующие env с владельцем выбранного тестового проекта.

## 2. Роли и ответственность

**Owner / Maintainer:** задаёт направление продукта, принимает ключевые архитектурные решения, согласует критичные изменения, порядок интеграции, миграции и релизы.

**Collaborator / Contributor:** выполняет согласованную задачу, отвечает за свой scope, совместимость с основной веткой, проверки и понятную передачу результата. Если для задачи нужен чужой или общий модуль, сначала согласует расширение границ.

**AI Coding Agent:** читает правила и релевантный контекст, следует контракту, переиспользует код, не меняет архитектуру самовольно, сообщает о неопределённости и ограничениях. Не объявляет проверки успешными без запуска и не выдаёт подмены за реальные интеграции.

Ответственный за задачу — координатор изменения, а не единоличный владелец соответствующих файлов навсегда. Доступы и право approve/merge назначаются отдельно владельцем репозитория, не этим Markdown-файлом.

## 3. Git Workflow

Уже принят процесс `feature/*` или `fix/*` → PR → проверки → merge в `main`. `main` — стабильный production, не личная рабочая ветка; прямой push в `main` не входит в процесс разработки.

1. Проверьте состояние checkout. Не стирайте чужие или незавершённые изменения командой reset/clean.
2. Получите актуальную `origin/main`, зафиксируйте полный SHA как `BASE_COMMIT` и создайте отдельную ветку.

```sh
git status --short --branch
git fetch origin
git rev-parse origin/main
# Скопируйте выведенный SHA в контракт задачи.
git switch -c feature/map-room-labels origin/main
```

Для исправления используйте, например, `fix/map-room-search`. Для нескольких независимых задач одного исполнителя подходят отдельные checkout/worktree. В одном общем checkout нельзя одновременно переключать ветки разных исполнителей.

3. Выполните задачу в пределах scope и применимые проверки из раздела 10.
4. Проверьте diff, явно выберите файлы, создайте commit и push.

```sh
git diff --check
git diff
git add CONTRIBUTING.md
git commit -m "docs: describe contribution workflow"
git push -u origin feature/contributing-guide
```

Команды выше иллюстрируют документационную задачу: используйте имя своей ветки и список её файлов. Не включайте секреты, зависимости, сборки или случайные правки через бездумный `git add .`.

5. Откройте PR в `main`, приложите контракт/manifest и результаты проверок. Передайте PR на ревью, исправьте замечания и повторите затронутые проверки.
6. Перед интеграцией согласуйте порядок связанных PR. Обновите ветку относительно текущей `origin/main` через обычный merge либо согласованный rebase, вручную разрешите конфликты и проверьте общий результат. Не переписывайте опубликованную общую ветку без согласования со всеми её участниками.
7. Maintainer сливает проверенные PR последовательно. После merge проверяются новая `main`, результаты CI/deployment и затронутый сценарий на целевом окружении.

**Новая рекомендация по именованию:** короткие ветки в нижнем регистре с дефисами; сообщения `feat:`, `fix:`, `docs:`, `test:` с конкретным результатом. В истории есть смешанные форматы коммитов; обязательного commitlint нет. Заголовок PR описывает итоговое поведение, при наличии добавляет Task ID. Не заявляйте Conventional Commits действовавшим строгим стандартом.

## 4. Task Contract

**Предлагается для существенных задач.** Контракт размещается в issue, описании PR или согласованном `TASK.md`; отдельный файл не обязателен. Существенны изменения нескольких модулей, общих интерфейсов, схемы/прав, внешних интеграций или пользовательских сценариев. Для небольшой независимой правки достаточно краткого scope и критериев в PR.

Пример контракта; заполните placeholders до начала работы:

```yaml
task_id: MAP-ROOM-LABELS
description: Подписи помещений по подтверждённой разметке
goal: Найти кабинет и открыть его карточку на нужном этаже
base_commit: <полный SHA origin/main на старте>
assignee: <согласованный исполнитель>
module: src/features/map
allowed_files:
  - src/features/map/data.ts
  - tests/college-map.test.ts
forbidden:
  - src/lib/auth
  - src/lib/supabase
  - supabase/migrations
  - src/features/ai
public_interfaces: MapRoom и CampusMap без изменения формы
api_contracts: Существующие маршруты и их параметры без изменений
dependencies: Подтверждённая разметка помещений от владельца
database: Без миграций и новых таблиц
security: Сохранить requireUser и server-only; исходные фото не публиковать
acceptance_criteria:
  - Каждый подтверждённый номер находится единственным результатом
  - Результат открывает соответствующий этаж и карточку
  - Неподтверждённые комнаты и маршруты не выдумываются
non_goals: Маршрутизация, изменение Auth, общий редизайн
```

Контракт должен явно описывать публичные types/interfaces, API и зависимости даже при отсутствии изменений. Если нужен файл вне списка, новая зависимость, изменение API или БД — опишите причину, потребителей и риск, получите согласование Maintainer/координатора связанных задач и обновите контракт **до** такой правки. Продолжайте независимую разрешённую часть работы, если это безопасно.

`BASE_COMMIT` сохраняет исходную точку задачи. После обновления ветки дополнительно укажите SHA, относительно которого проверена интеграция; не подменяйте историю старта задачи.

## 5. Предотвращение конфликтов

- До параллельного старта перечислите пересечения файлов и назначьте ответственного за каждое общее изменение.
- Не редактируйте несогласованно один shared-компонент, тип БД, миграцию или глобальную конфигурацию в нескольких задачах.
- Не меняйте публичный интерфейс без поиска потребителей и плана совместимости. Добавочные optional-поля обычно безопаснее удаления или смены значения существующего поля, но тоже требуют проверки потребителей.
- Не переписывайте чужую реализацию ради собственного удобства и не форматируйте файлы за границами задачи.
- При конфликте разберите назначение обеих правок. Не выбирайте целиком `ours`/`theirs` без проверки поведения, импортов, типов, SQL и тестов.
- Не сливайте одновременно несколько крупных конфликтующих веток. После первого merge обновите зависимую ветку и повторите её затронутые проверки.

**Пример связанных задач:** один исполнитель расширяет контракт сообщений, другой делает их UI. Сначала согласуются поля, ошибки, права и совместимость со старым UI. Контракт/RPC/миграцию меняет назначенный исполнитель. UI-ветка зависит от конкретного PR или проверенного commit; подмена допускается только как явно обозначенный локальный тест. Сначала интегрируется совместимая основа, затем обновлённая UI-ветка. Пользовательский сценарий проверяется после объединения.

## 6. Архитектурные границы

Текущая основа — модульный монолит: Next.js App Router/React/TypeScript на Vercel, Supabase Auth, PostgreSQL/RLS и Supabase Storage. Серверная логика приложения находится в Next.js; отдельного обязательного backend deployment для социальной части нет.

| Зона | Назначение |
| --- | --- |
| [src/app](src/app/) | Страницы, layouts, loading/error boundaries, Auth callbacks и Route Handlers. |
| [src/features](src/features/) | Запросы, формы, валидация и Server Actions предметных модулей. |
| [src/components](src/components/) | Общие UI-примитивы, оболочка, бренд и навигация. |
| [src/lib/auth](src/lib/auth/), [src/lib/supabase](src/lib/supabase/), [src/proxy.ts](src/proxy.ts) | Проверка пользователя, клиенты Supabase и обновление cookie. |
| [src/lib/storage.ts](src/lib/storage.ts) | Общие операции загрузки и проверки файлов. |
| [src/types/database.ts](src/types/database.ts) | Контракты таблиц и RPC приложения. |
| [supabase/migrations](supabase/migrations/) | Версионируемая схема, ограничения, RPC, triggers и политики доступа. |

Без согласования нельзя менять стек, Auth, общий data layer, публичные API/types, маршрутизацию вне задачи, удалять рабочие модули, добавлять альтернативные backend-сервисы или скрыто менять глобальные настройки. Новая зависимость должна решать конкретную задачу, иметь проверенную совместимость и попадать вместе с lock-файлом в ревью.

К общим критичным зонам относятся Auth/Proxy, Supabase clients, Storage, типы БД/RPC/RLS, общий community layout с аудиопровайдером, навигация, `globals.css`, `package.json`/lock, конфигурации и CI. Их изменение требует согласованного владельца правки и проверки зависимых модулей; этот список не является настроенным `CODEOWNERS`.

Сохраняйте границу Server/Client Components: серверные модули и секреты не импортируются в клиент. Не переносите серверную сессию в общий singleton или общий кэш между пользователями. Профиль, сообщения и чужой доступ не должны зависеть только от видимости кнопок.

## 7. База данных, права и файлы

- Используйте новые миграции `supabase/migrations/YYYYMMDDNNNN_description.sql` по существующему формату. Согласуйте уникальный префикс с параллельными задачами; применённые файлы не редактируйте и не переименовывайте.
- Описывайте таблицы/поля, индексы, ограничения, grants, RPC и RLS вместе; обновляйте `src/types/database.ts`, запросы и тесты. Не создавайте вторую таблицу или RPC для уже решённого сценария.
- Изменяйте схему совместимо с ещё работающей версией приложения. Для удаления/переименования поля нужны план перехода, миграция данных и согласованный порядок выпусков. План восстановления не должен сводиться к уничтожению production-данных.
- Сначала применяйте миграцию к отдельной тестовой базе/проекту. Проверяйте владельца, другого вошедшего пользователя и анонимного клиента, включая прямой запрос без UI. Для чатов отдельно проверяйте постороннего, который не состоит в диалоге.
- Производственную миграцию согласует и выполняет уполномоченный участник до выпуска зависимого кода. Сверяйте историю SQL Editor/CLI, результат и целевой проект. Не запускайте reset существующего production-проекта.
- В каждом Server Action и изменяемом API проверяйте пользователя и серверную валидацию; владельца определяйте сессией/`auth.uid()`, не UUID из формы. Proxy обновления cookie не заменяет эту проверку. Сохраняйте RLS, ограничения SQL и проверки security-definer функций.
- Секреты — только в игнорируемых env или серверных настройках окружения. Не коммитьте `.env.local`, `.env.test.local`, credentials, auth cookies, токены, пароли или дампы реальных данных. Из публичного URL не следует допустимость публикации signed URL с токеном.
- Переменные `NEXT_PUBLIC_*` доступны браузеру. Туда нельзя помещать secret/service-role/provider keys. Не используйте привилегированный ключ вместо исправления RLS; социальный data layer работает с сессией пользователя.
- Переиспользуйте Storage helper и реальные лимиты модуля. Проверяйте размер, MIME, владельца пути и метаданные загруженного объекта; не доверяйте одному расширению или данным формы. Не ослабляйте bucket policies ради загрузки.
- `avatars` и `post-media` используются как public media с ограничением записи; `post-files`, `message-files`, `audio`, `dating-photos` — private. Private URL создаётся ограниченным по времени и только после чтения разрешённого через RLS пути. Не помещайте такие URL в общий кэш, логи или репозиторий.
- При сбое загрузки/удаления сохраняйте понятное состояние и возможность повтора; описывайте частичный результат между Storage и БД. Не выдавайте успешный тест с подменой Storage за реальную загрузку в Supabase.
- AI получает только разрешённый контекст AI-диалога. Сохраняйте существующие проверки сессии/Origin/объёма и постоянные квоты; не логируйте личные вопросы, ответы и ключи. Менять провайдера, лимиты или способ хранения истории можно только в соответствующей согласованной задаче.

## 8. Frontend и общий UX

- Переиспользуйте [src/components/ui](src/components/ui/), общий layout и токены [src/app/globals.css](src/app/globals.css). Не создавайте независимую дизайн-систему внутри модуля.
- Проектируйте от мобильной ширины, затем проверяйте desktop: навигацию, доступность кнопок, переполнение, длинные подписи, клавиатуру и видимый focus.
- Сохраняйте типизацию TypeScript (`strict`, без необоснованного `any`), alias `@/*` и точный регистр путей. Изменение shared types согласуется с потребителями.
- Для асинхронного сценария предусматривайте loading, empty, error и success states, повтор и сохранение пользовательского ввода при ошибке, где это применимо.
- Держите интерактивное состояние локально по существующим границам. Избегайте лишних запросов и перерисовок, но не вводите общий кэш приватных данных или оптимизацию без установленной проблемы.
- Сохраняйте визуальную идентичность NEXUS и действующие сценарии соседних модулей. Указывайте реальные размеры браузерной проверки; эмуляция мобильной ширины не доказывает работу физического телефона.

## 9. Работа ИИ-агента

1. Прочитайте `AGENTS.md`, актуальное состояние и нужные разделы документации; не перечитывайте весь репозиторий без причины.
2. Проверьте branch/status и найдите действующую реализацию; отличайте `main`, экспериментальную ветку и опубликованную версию.
3. Уточните контракт, scope и Non-goals. Составьте короткий план, если есть зависимости или несколько этапов.
4. Переиспользуйте существующие функции, типы и тесты; вносите локальные изменения без самовольного архитектурного рефакторинга.
5. Согласуйте выход за контракт и критичные изменения до их выполнения; при противоречии инструкций сообщите его Maintainer.
6. Проверяйте результат фактически, а не только по отсутствию ошибки инструмента. Не отключайте проверки и защиту ради зелёного статуса.
7. Не маскируйте исключения, не подменяйте реальные интеграции mocks и не называйте ненастроенный сервис работающим.
8. Выполняйте проверки после связанного блока работы; повторяйте только затронутые исправлением проверки. Не пересказывайте неизменённые файлы.
9. Не публикуйте секреты, приватные данные и пользовательские сообщения в логах, примерах или отчётах.
10. Передайте краткий проверяемый итог: что изменено, какие проверки выполнены, ограничения, PR и следующий необходимый шаг.

## 10. Проверки и Code Review

Перед передачей PR выполните существующие команды:

```sh
npm run typecheck
npm run lint
npm test
npm run build
git diff --check
```

Для небольшого цикла исправления запускайте связанные тесты, например:

```sh
node --experimental-strip-types --test tests/college-map.test.ts
```

CI [Checks](.github/workflows/check.yml) запускает Node.js 24 на Ubuntu, `npm ci` и четыре npm-проверки выше; job называется `build`. ESLint использует существующие Next.js core-web-vitals/TypeScript rules и запрещает предупреждения командой lint. Отдельных обязательных markdownlint, commitlint, генератора контрактов или merge queue в коде не настроено.

Для затронутых сценариев добавьте применимую браузерную/e2e-проверку. Playwright настроен в [playwright.config.ts](playwright.config.ts):

```sh
npx playwright install chromium
npm run test:e2e
```

Не запускайте записывающие live-сценарии на общей production-базе. Их параметры, отдельные аккаунты, побочные эффекты и очистка описаны в `docs/TESTING.md`; пропущенный live-тест не считается пройденным. Unit/PGlite/mocked/browser/real-Supabase/physical-device проверки указываются раздельно.

Дополнительно проверьте импорты и маршруты, потребителей изменённых интерфейсов, серверную валидацию/права, миграции, приватность Storage, env и отсутствие секретов. Для документации проверяйте относительные ссылки, команды и соответствие коду; не создавайте тесты, которые просто повторяют текст документа.

Если проверка не выполнена, укажите команду, причину и что остаётся неподтверждённым. Ошибки обязательных проверок и блокирующие замечания запрещают считать PR готовым к merge; отсутствие инструмента не превращает ошибку в успех. Новые проверки не объявляйте уже обязательными без согласования.

**Чеклист исполнителя:**

- [ ] Scope и базовый SHA указаны; общие файлы согласованы.
- [ ] Diff содержит только нужные файлы, без секретов и случайных изменений lock/config.
- [ ] Контракты, RLS и соседние сценарии сохранены или изменения согласованы.
- [ ] Применимые проверки выполнены; пропуски и подмены обозначены.
- [ ] PR содержит способ интеграции и известные ограничения.

**Чеклист ревьюера:**

- [ ] Изменение решает согласованную задачу и не расширяет архитектуру без причины.
- [ ] Проверены потребители shared interfaces, безопасность и порядок миграции/deploy.
- [ ] Доказательства соответствуют заявленному результату, обязательные проверки зелёные.
- [ ] Конфликты разобраны, блокирующие замечания устранены, порядок merge согласован.

Ревьюер оставляет конкретные замечания с местом, причиной и критерием исправления. Исполнитель исправляет их либо аргументированно согласует другое решение. Изменения после ревью требуют повторной проверки затронутой части; нельзя сливать иной commit, выдавая прежние результаты за его проверки.

## 11. Integration Manifest и пример PR

Для существенной задачи PR должен содержать: результат, список изменённых файлов, публичные интерфейсы/API и их потребителей, зависимости/lock, env, миграции и порядок применения, выполненные проверки, ограничения, порядок интеграции и восстановления при неудаче.

Этого может быть достаточно в описании PR. `TASK.md`, `CHANGED_FILES.md`, `INTEGRATION.md`, `TESTS.md` допустимы как согласованные дополнительные материалы большого handoff, но сейчас не являются обязательным комплектом репозитория. Не создавайте их для тривиальной правки. Исполняемый SQL храните в `supabase/migrations`, не дублируйте его отдельным корневым `MIGRATION.sql`.

Пример корректного заполнения PR; результаты ниже — иллюстрация формата, не заявление о выполненных тестах:

```markdown
## MAP-ROOM-LABELS — номера помещений на карте
Цель: поиск подтверждённого кабинета открывает правильный этаж и карточку.
BASE_COMMIT: <полный SHA>
Ответственный: <исполнитель>; согласование shared-файлов: не требуется.

Изменено: src/features/map/data.ts, tests/college-map.test.ts.
Контракты/API, зависимости, env, БД: без изменений.
Non-goals: маршруты и редизайн.

Проверки: <команды, ОС/Node.js, pass/fail/not run и причины>.
Браузер: <что проверено, URL/commit и размеры; подмена или реальные данные>.
Ограничения: подтверждены подписи, но не фактическая доступность помещений.

Интеграция: <порядок зависимых PR, миграций и deployment; если нет — явно>.
После merge: <сценарий проверки на основном адресе>.
При сбое: <согласованный revert/rollback без уничтожения данных>.
```

## 12. Definition of Done

| Состояние | Что оно означает |
| --- | --- |
| Код написан | Изменение есть в ветке; проверки, ревью и интеграция ещё могут отсутствовать. |
| PR готов | Acceptance Criteria выполнены, контракт соблюдён, проверки и документация готовы, блокирующие замечания сняты. Merge ещё не подтверждён. |
| Задача интегрирована | PR принят, проверены новая основная ветка и применимое окружение/пользовательский сценарий после интеграции. |

Для завершения нужны выполненные Acceptance Criteria, сохранённая архитектура и функциональность, применимые успешные проверки, документация и отсутствие блокирующих замечаний. В handoff разрешено остановиться на состоянии «PR готов», если задача не включает merge/release; укажите этот статус прямо.

`main` связан с production Vercel, feature/PR — с Preview. Preview может использовать ту же Supabase БД и поэтому не гарантирует изоляцию данных. Успешный build или merge не доказывает публикацию: после релиза проверьте статус точного commit/deployment и затронутый сценарий на основном HTTPS-адресе из `PROJECT_STATE.md`. Production env, Auth redirects, секреты, миграции и релизы согласуются отдельно; создание PR не разрешает менять доступы или покупать ресурсы.

## 13. Документация, разногласия и развитие правил

- После значимой функции кратко обновляйте `PROJECT_STATE.md`: фактическое поведение, проверки, deployment/status и ограничения. Не превращайте его в журнал всех команд; небольшая документационная правка может быть описана в PR.
- При согласованном изменении границ модулей, API, схемы или security-модели обновляйте соответствующий архитектурный раздел вместе с кодом и примерами потребителей.
- Новое соглашение оформляйте отдельным предложением в PR: причина, затронутые участники, отличие от текущего правила и критерий принятия. Архитектурные контракты утверждает Maintainer с участием исполнителей зависимых модулей.
- Не копируйте целиком AGENTS в CONTRIBUTING. При одобрении нового правила укажите его основной источник и согласуйте связанные документы, чтобы не держать две разные версии одного требования.

### Найденные расхождения — требуют отдельного решения

Проверено по основной ветке на момент подготовки документа. Перечисленные документы этим PR не исправляются.

| Источник | Что не совпадает с текущим состоянием |
| --- | --- |
| `README.md`, «Что уже есть в коде» | `/map` и `/ai` названы заглушками, хотя страницы и модули реализованы. |
| `README.md`, Development | Репозиторий назван private; API GitHub при проверке показывает PUBLIC. Не полагайтесь на приватность исходников как на защиту секретов. |
| `README.md`, быстрый запуск БД | Инструкция с одной core-миграцией не разворачивает всю текущую схему с последующими миграциями. |

`NEXUS_CONTEXT.md`, `TASK.md`, `docs/BLUEPRINT.md` и `docs/DATABASE.md` при проверке отсутствуют. Их наличие не является условием начала работы; схема проверяется по миграциям/типам и архитектурному описанию. Непринятые ветки, включая подготовку self-hosted AI, не описываются как возможности основной версии.

### Что предлагается утвердить

Дополнения этого документа: контракт существенной задачи и `BASE_COMMIT`, ответственный за пересечения shared-файлов, согласование расширения scope, обязательное ревью критичных зон, последовательная интеграция связанных PR и manifest в PR. Форматы commit/названий остаются рекомендацией, пока Maintainer не утвердит иное. Эти организационные договорённости не меняют работающие Auth, RLS и публичные контракты сами по себе.

### Что настраивается отдельно в GitHub

При этой проверке API эффективных branch rules для `main` вернул пустой список, classic protection — `Branch not protected`. Workflow запускает `build`, но это не означает, что merge технически заблокирован при его ошибке. Возможности зависят от прав аккаунта и настроек репозитория.

Рекомендации для Owner/Maintainer, **не выполненные этим документом**:

1. Включить ruleset/branch protection для `main`: только PR, обязательный успешный `build`, ограничить обход правил, direct/force push и удаление ветки.
2. Требовать хотя бы одно одобрение и разрешение обсуждений; определить повторное одобрение после существенных изменений. При необходимости согласовать и добавить `CODEOWNERS` для критичных зон, не назначая людей без их подтверждения.
3. Разграничить права collaborators и доступ к production env/БД/Vercel; определить, кому доступны миграции и релизы. Проверить условия запуска workflow и выдачи секретов недоверенным PR.

Markdown не обеспечивает эти ограничения технически, не проверяет фактическую схему удалённой БД, не изолирует Preview и не предотвращает гонки редактирования. Для этого нужны реальные права, настройки платформ, проверки и соблюдение согласованного процесса.
